## Reading

- The host is CPU-bound at about 124 req/s. Latency is queueing: p50 is already 1.3 s, and cache
  hits are as slow as misses, so the cost is the Python request path itself, not the database.
- A `304` still runs the whole FastAPI stack (rate limiter, ETag, Redis lookup) on the one core.
- Runbook step 1 (`-w 3`) won't help: the core is already busy, and a third worker only adds
  context switches. Step 2 doesn't apply, because misses and hits are equally slow.
- What's left is SD §11's contingency: Caddy answers `/v1/live` from a short-lived cache, so most
  polls never reach Python. That needs a custom Caddy image (B2) and the owner's go-ahead (runbook
  step 3). The other lever is more cores for VPS-1. SD §2 treats 2 OCPU / 12 GB as the
  whole free allowance, but Oracle has published the Ampere A1 Always Free limit as 4 OCPU / 24 GB.
  If the account's limits page confirms that, resizing VPS-1 to 2–3 OCPU costs nothing. Check it
  before choosing.
